Auth0 MCP demo: who can call what, and what gets refused

  Three local services are running:
    issuer       stands in for Auth0 and signs real RS256 tokens   http://localhost:63026/
    MCP server   the agent's tools, protected by those tokens      http://localhost:63027/mcp
    reports API  a backend the MCP server calls for the user       http://localhost:63028

  Six requests follow. Requests 1-3 and 5-6 should be refused; request 4 is the one allowed path.

────────────────────────────────────────────────────────────────────────
 REQUEST 1 of 6 · No token
────────────────────────────────────────────────────────────────────────
  Try:     Call the MCP server with no access token at all.
  Send:    POST /mcp   (no Authorization header)
  Result:  401 Unauthorized   PASS
           WWW-Authenticate: Bearer resource_metadata="/.well-known/oauth-protected-resource", scope="read:reports read:github"
  Why:     The 401 points the client at the metadata and names the scopes to ask for, so it can log in by itself.

────────────────────────────────────────────────────────────────────────
 REQUEST 2 of 6 · Wrong audience
────────────────────────────────────────────────────────────────────────
  Try:     Send a real, correctly signed token that was issued for a different API.
  Send:    POST /mcp   Bearer <token>   aud = https://someone-else.test/
  Result:  401 Unauthorized   error="invalid_token"   PASS
  Why:     Signed isn't enough: the token must be issued for this server, so it can't be replayed here.

────────────────────────────────────────────────────────────────────────
 REQUEST 3 of 6 · Missing permission
────────────────────────────────────────────────────────────────────────
  Try:     Send a valid token for this server, but without read:reports, and call read_report.
  Send:    tools/call read_report {week: "2026-W43"}   Bearer <token>   scope = "openid profile"
  Result:  403 Forbidden   error="insufficient_scope"   scope="read:reports"   PASS
  Why:     Known user, not allowed. The 403 names the missing scope, so the client knows what to ask for.

────────────────────────────────────────────────────────────────────────
 REQUEST 4 of 6 · Allowed: on-behalf-of token exchange
────────────────────────────────────────────────────────────────────────
  Try:     The same call, now with read:reports. Watch what the MCP server does for the user.
  Send:    tools/call read_report {week: "2026-W43"}   Bearer <token>   aud = https://reports.demo.test/
           1. MCP server checks issuer, signature, audience, expiry and the read:reports permission
           2. MCP server -> issuer: token exchange (RFC 8693), new audience https://reports-backend.demo.test/
              same user: auth0|demo-user
           3. MCP server -> reports API: GET /reports/2026-W43 with the exchanged token
  Result:  200 OK   "Report for 2026-W43: build passed; tickets closed: AUTH-103"   PASS
  Why:     The user's token is never forwarded. The backend gets a token issued for it, for the same user.

────────────────────────────────────────────────────────────────────────
 REQUEST 5 of 6 · Token passthrough blocked
────────────────────────────────────────────────────────────────────────
  Try:     Skip the MCP server: send the user's MCP token straight to the reports API.
  Send:    GET /reports/2026-W43 (reports API)   Bearer <token>   aud = https://reports.demo.test/, has read:reports
  Result:  401 Unauthorized   {"error":"invalid_token"}   PASS
  Why:     Only the exchanged token works. No token passthrough, no confused deputy.

────────────────────────────────────────────────────────────────────────
 REQUEST 6 of 6 · Bad input
────────────────────────────────────────────────────────────────────────
  Try:     Send broken JSON, then a body over the 1 MB limit, then check the server still answers.
  Send:    POST /mcp   body "{not json"
           POST /mcp   body of 1 MB + 16 KB
           whoami on a fresh connection
  Result:  400 Bad Request   (JSON-RPC parse error)   PASS
           413 Payload Too Large
           whoami answered: server still up
  Why:     Clean, named errors, and the server keeps serving.
